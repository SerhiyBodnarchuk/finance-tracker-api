  Notes on judgment calls made during implementation:

  1. [JsonPropertyName("transactionType")] applied to the `Type`
     property on both TransactionCreateRequest and TransactionResponse.
     The README's example payloads (and spec FR-027 / US3 Independent
     Test) require the wire-form field to be `transactionType`, not
     `type`. With the camelCase naming policy in
     JsonSerializationOptions.Default, the default would collide on
     `type`. Used the records' [property: JsonPropertyName(...)]
     attribute target so the positional property carries the
     annotation. On report DTOs (ReportRequest / ReportResult /
     ReportType), `Type` correctly serializes as `type` (matching the
     README examples), so no annotation is needed there.

  2. TransactionMapper.ToResponse uses an explicit for-loop over
     CategoryIds rather than LINQ Select(...).AsReadOnly(), so the
     KeyNotFoundException is thrown at the moment the missing id is
     encountered (not when an enumerator is later materialized). This
     also makes the error path step-debuggable. The result is wrapped
     in `.AsReadOnly()` to enforce the read-only contract surface.

  3. Tests use `Assert.Collection` for the ordered breakdown
     assertion in ReportResultRoundTripTests rather than a single
     `Assert.Equal(expected[], actual[])`, so any breakdown ordering
     regression in the future will show a precise per-position
     diagnostic.

Prompt:
  User reported: POST /api/categories with body {"name":"First_test",
  "type":3} succeeds and saves the record; the listing shows
  "type": 3 (raw integer) for the new record. The numeric value 3
  is outside the CategoryType enum range (which has Income=0,
  Expense=1, Both=2).

Root cause:
  System.Text.Json's JsonStringEnumConverter accepts integer values
  by default. With allowIntegerValues=true (the constructor default),
  any int parses to the enum via direct cast - even values outside
  the declared enum range. The cast itself doesn't fault because
  C# enums are int-backed and accept any int. The bug surfaces only
  on the way back out: there's no enum name for value 3, so the
  serializer writes it as raw 3 in JSON.

Fix:
  Finance.Business/JsonSerializationOptions.cs - changed the
  registered converter from `new JsonStringEnumConverter()` to
  `new JsonStringEnumConverter(namingPolicy: null,
  allowIntegerValues: false)`. The single edit propagates everywhere
  because:
   - Program.cs's AddControllers().AddJsonOptions(...) copies the
     converters from JsonSerializationOptions.Default into the MVC
     pipeline, so model binding now rejects integer enums with HTTP
     400 (ValidationProblemDetails from [ApiController]).
   - Integration tests serialize via the same
     JsonSerializationOptions.Default.
   - The round-trip unit tests use the same options for both ends of
     the round-trip.

  The fix applies to all enums that flow through this options
  instance: CategoryType, TransactionType, ReportType. The bug
  existed for every one of them.

Fix:

  transformer:

    options.AddSchemaTransformer((schema, context, _) =>
    {
        var type = context.JsonTypeInfo.Type;
        if (type.IsEnum)
        {
            schema.Type = JsonSchemaType.String;
            schema.Format = null;
            schema.Enum = Enum.GetNames(type)
                .Select(name => (JsonNode)JsonValue.Create(name)!)
                .ToList();
        }
        return Task.CompletedTask;
    });

  (flags enum in Microsoft.OpenApi namespace), schema.Enum is
  List<JsonNode> (uses System.Text.Json.Nodes). First attempt with
  the older OpenApiString/IOpenApiAny shape failed to compile -
  those types are gone in 2.x.
